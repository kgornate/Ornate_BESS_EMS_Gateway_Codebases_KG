# Kalpa Central Sync local generation monitor v0.1

This adds a terminal dashboard and a separate local producer harness. It does not enable production Central Sync. It reuses the installed S1/S2/S3/S4/S8/S10 producer classes against the local API and writes messages to /var/lib/kalpa-central-monitor/outbox.db.

No uploader, backend HTTP client, remote-command processor or archive replay service is started. The source Central Sync config remains disabled/unchanged; the harness intentionally starts only configured producer loops. Local API credentials come from the existing systemd EnvironmentFile and are never copied into the package/config output. S2 uses the installed checksum-pinned manifest.

Install on DEBIX:

```bash
cd /root
tar -xzf kalpa-central-monitor-v0.1.tar.gz
bash /root/kalpa-central-monitor-v0.1/install.sh
kalpa-sync-monitor
```

Use Ctrl+C to leave the dashboard. The background generator keeps running. Stop it after observation:

```bash
systemctl stop kalpa-central-generation
```

Start it again:

```bash
systemctl start kalpa-central-generation
kalpa-sync-monitor
```

The service is not enabled at boot. To inspect errors:

```bash
journalctl -u kalpa-central-generation -n 40 --no-pager
kalpa-sync-monitor --once
```

Dashboard record/message/error counters describe the current generator process. Rates use deltas between observations and reset after restart. The SQLite outbox message counts/payload sizes are cumulative across runs. The dashboard marks stale status when the generator stops. S4/S8 may remain at zero until a new event/configuration change; S5/S6/S7 are application-dependent and S9 needs executed commands, so they are not generated by this harness. The newly integrated ACREL meter is still outside frozen S2 utility_meter mapping.

The test outbox has a nominal 256 MiB SQLite capacity and a 512 MiB free-space requirement. It is not a long-term historian. No automatic upload, ACK, pruning or archive deletion is performed. When capacity is exhausted, new enqueue attempts can fail: stop generation and preserve/export the test data before choosing a cleanup policy. Existing application history, five-day SD planning and the production outbox are separate.

With the gateway currently in mock mode, generated BESS telemetry is simulated. A disconnected physical meter can keep the backend health degraded without breaking simulated BMS/PCS generation. This monitor does not change backend polling, control/write gates, WiFi, Ethernet, Cloudflare or production upload settings.
